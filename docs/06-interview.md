# 简历与面试讲解

## 可用项目描述

个人项目：供应链运营与发货准备核验Agent。基于Spring Boot、MySQL、FastAPI与Vue，围绕库存查询、补货依据解释、人工采购复核及表单只读核对构建业务链路；Java统一负责业务数量、权限、幂等与事务，Agent负责意图理解、工具编排及知识引用。

可选亮点（仅写自己能展开的部分）：

- 补货结合固定日期销量、安全库存、交货提前期和箱规，输出计算依据与需复核/数据不足状态，避免把规则建议当作采购承诺。
- 将同请求幂等与SKU级pending去重分开，在事务中按SKU顺序加锁；浏览器保留未知结果的原始内容和幂等键，支持刷新后核对重试。
- 以独立reader身份接入表单只读HTTP查询，隔离采购与审批写入；使用Pi SDK和Faux场景验证审批、幂等回填及回查故障。

## 90秒主线

实习里接触到自动更新流程后，我发现难点不只是把任务跑起来，而是失败后能否判断做到了哪一步。个人项目把这一问题具体化成库存运营：先展示可信事实，再计算有依据的补货建议，由人决定采购。重复请求不能重复建单，换一个请求键也不能绕过已有待处理意向；网络超时则保留原请求核对。发货准备有独立审批，我只把核验结果接到运营台查看，不把采购确认说成库存已补足或商品已发货。

## 必须能回答

为什么提前期不再加一次？为什么安全库存有可能高于销量需求？为什么整箱取整不改变紧急度？同键重试与不同键冲突如何区分？为什么锁商品行？批量有一个冲突是否部分写入？提交后断网如何判断？确认后为何仍不能计算在途库存？为什么用只读reader而不转发JWT？为什么30/30不是模型准确率？

目前仍需补足真实模型验证、零销量与采集缺失区分、在途与收货闭环。可以主动讲出限制及取舍，不使用虚构上线效果、用户量或提升百分比。
